# Документація CI/CD процесів проєкту UnitTestingDemo

## 1. Перелік Workflows та їх призначення
* **CI (`ci.yml`)**: Автоматична збірка, перевірка форматування коду утилітою `dotnet format`, збірка з параметром суворого відстеження попереджень (`-warnaserror`) та кросплатформене тестування на матриці операційних систем.
* **Docker Build (`docker.yml`)**: Автоматизація збірки Docker-образу на базі створеного Dockerfile та запуск Smoke-тесту для підтвердження цілісності середовища.
* **Manual Release (`manual-release.yml`)**: Сценарій ручного запуску релізу застосунку з параметризацією вибору цільового інвайронменту (staging/production) та тегу версії.

## 2. Тригери автоматизації
* `push` / `pull_request` на гілку `main` — для запуску інтеграційних перевірок коду.
* `workflow_dispatch` — для ручного менеджменту випусків через інтерфейс GitHub Actions.

## 3. Принцип роботи Matrix Strategy
Використовується комбінація ОС `[ubuntu-latest, windows-latest]` та версій SDK `['8.0.x', '9.0.x']`. Це дає змогу ізольовано та паралельно виконати 4 різні збірки, що ліквідує ризик виникнення специфічних помилок сумісності платформ на етапі розгортання.

## 4. Зберігання артефактів
Звіти покриття коду тестів (`coverage.cobertura.xml`) автоматично архівуються архіватором GitHub Actions за допомогою action `actions/upload-artifact@v4` і доступні для завантаження протягом 14 днів у меню виконаного пайплайну.

## 5. Відповіді на контрольні питання
1. **CI відрізняється від CD** тим, що CI фокусується на валідації змін розробника (збірка, тести, якість коду), а CD — на автоматичній доставці стабільного релізу до користувача чи сервера. У нашому проєкті CI реалізовано повністю, а CD — на етапі підготовки релізних артефактів та Docker-образів.
2. **Matrix strategy потрібна** для автоматичного тестування коду в різних конфігураціях середовищ (різні ОС, різні версії рантаймів), запобігаючи багам типу "працює лише на моєму комп'ютері".
3. **Artifacts — це збережені файли збірки**. Звіти покриття коду зберігають як артефакти для аналізу динаміки якості проєкту та інтеграції з аналітичними системами (SonarQube).
4. **Branch protection + required checks** блокують можливість зробити злиття (Merge) Pull Request у гілку `main`, якщо автоматичні тести або лінтери завершилися з помилкою. Це тримає головну гілку завжди в робочому стані.
5. **Різниця тригерів**: `push` реагує на надходження коду в гілку, `pull_request` — на намір об'єднати гілки для їх попереднього тестування, `workflow_dispatch` — повністю ручний запуск користувачем.
6. **Docker build у CI корисний** навіть без деплою, оскільки він перевіряє валідність інфраструктурного коду (`Dockerfile`), правильність копіювання файлів та успішність старту застосунку в чистій ізольованій операційній системі.
